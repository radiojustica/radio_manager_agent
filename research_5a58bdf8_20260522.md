# Research: Refatoração do WorkerManager e WebSocket Events

**Date**: 2026-05-22

## 1. Executive Summary
A arquitetura atual de monitoramento e eventos é baseada em polling ineficiente e acoplamento direto com uma instância global (`guardian_instance`). O `WorkerManager` carece de um mecanismo de notificação de eventos em tempo real, e o servidor WebSocket (`api/manager.py`) opera com um loop de 1 segundo por conexão, re-importando módulos e consultando o estado de forma redundante.

## 2. Technical Context
- **WorkerManager (`worker_manager.py`)**: Gerencia o ciclo de vida dos workers usando `apscheduler`. Executa ciclos via `run_cycle`, mas não emite eventos descritivos de início/fim/sucesso para consumo externo, limitando-se a logs e registros no `RewardStore` em caso de falha.
- **GuardianService (`services/guardian_service.py`)**: Centraliza o log de eventos via `log_event`. Mantém uma lista `events_list` em memória (máximo 100 itens).
- **WebSocket (`api/manager.py`)**: Endpoint `/ws/status` utiliza a classe `ConnectionManager`. A implementação atual do handler `websocket_endpoint` possui um loop `while True` que consome recursos desnecessariamente ao realizar polling no `guardian_instance` a cada segundo.
- **Front-end (`frontend/src/components/EventTicker.jsx`)**: Consome o WebSocket e espera um JSON com a chave `events`.

## 3. Findings & Analysis
- **Ineficiência do WebSocket**: O padrão atual de "polling-over-websocket" anula os benefícios de baixa latência e eficiência do protocolo.
- **Falta de Observabilidade nos Workers**: Não há rastro em tempo real de qual worker está rodando, apenas o resultado final ou erros críticos.
- **Acoplamento**: Muitos componentes dependem diretamente da importação do `guardian_instance` para registrar eventos, dificultando a modularização.

## 4. Technical Constraints
- A retrocompatibilidade com o frontend é necessária (o formato do JSON `{"events": [...]}` deve ser mantido ou estendido).
- O limite de memória para eventos deve ser respeitado para evitar vazamentos em execuções longas.

## 5. Architecture Documentation
- O sistema utiliza `FastAPI` para a API e `apscheduler` para tarefas em background.
- O padrão de eventos atual é síncrono e baseado em mutação de estado global.
